## 2. 设计前数据链路（入口 → 状态 → 副作用）

**链路 A：采集中实时命中 → 文档**
`adb logcat` 行 → `follow::emit`（`book.prepare→ring.push→book.commit`）→ `batcher.note` → `log/hits` 事件 → `@yohu/api.onLogHits` → `capture-subscriptions.onLogHits` → `workspace.applyHits` → `panel-projection.applyHits→appendToSession→applyAppend→writePanel` → store `visible` → `LogDocument.sync` → `LineBoard.project` → `EditorView`。
证据：代码位置全链存在；运行观察＝`store.test.ts` 命中管线用例 + `document/board` 用例（已验证）。

**链路 B：换过滤 / 溢出 / 重新可见 → 整页装入**
`patchFilter / onLogOverflow / resumeVisible / setFollowing(true)` → `viewport-page.loadPage` → `log.window.bind`（绑定时刻 `through=ring.next_seq()`，只含 `seq<=through-1`）→ `panel-projection.applyPage` → store `visible`。
证据：代码位置 + `store.test.ts` 过滤/溢出用例（已验证）。

**链路 C：命中空洞（丢批）**
`batcher.try_send` 满 → 丢推送、`log/overflow` 计数 → UI 侧此前只能靠 overflow 事件整页重绑。
证据：`batch.rs::push/emit_overflow` + `capture-subscriptions.onOverflow`；运行观察＝溢出用例（已验证）。缺陷证据见 §4。

## 4. 问题清单（阶段内闭合；级别只排顺序）

### P0-1（Stage1 已闭合）双通道 + `bumpPage` 临时对账导致丢行
- 文件：`capture-subscriptions.ts`（旧 `onLogHits` 调 `viewport.bumpPage`）、`viewport-page.ts`（`pageGen/bumpPage`）、`panel-projection.ts`（`applyPage` 盲替换）。
- 正确层：store·文档投影。
- 处置：删除 `bumpPage` 双代际；`applyPage` 改为按 seq 对账（保留页末之后已画行且命中当前过滤）；命中事件不再参与页代际。证据：`store.test.ts`「溢出回补遇上并发命中…不丢行」修复前 `[0,1,4]`、修复后 `[0,1,2,3,4]`（已验证）。

### P1-1（Stage1 已闭合）空洞只靠 `log/overflow` 被动恢复
- 文件：`capture-subscriptions.ts::onOverflow`（唯一恢复入口）。
- 正确层：store·事件入口。
- 处置：新增 `healGap(windowId, firstSeq)`——命中首 seq 越过窗口已见末 seq 时主动 `loadPage` 对账，不依赖 overflow 事件（其可能被满队列延迟/丢失）。证据：`store.test.ts`「命中空洞（无 overflow 事件）自动按 seq 对账补齐」（已验证）。

### P1-2（Stage2 已闭合）`applyAppend` 对 `seq<=after` 静默丢弃
- 文件：`stream/log-window-reducer.ts::applyAppend`。
- 正确层：store·文档状态机。
- 处置：连续 seq 判定归 reducer——命中首 seq 越过已画末行即返回 `gap{fromSeq,toSeq}`，`panel-projection.appendToSession` 收到 gap 触发一次 `log.window.bind` 回环补齐；不再静默丢。`applyAppend` 单测覆盖「连续无空洞 / 报告空洞区间 / 首次不误报 / 暂停与未开始不更新」。

### P1-3（Stage2 已闭合）文档状态分属多模块、双套增量算法
- 文件：`stream/log-window-reducer.ts`（新，唯一纯状态机）；`panel.ts` 降为薄门面（`export *`）；`panel-projection.ts` / `follow-state.ts` 只做装配（`follow-state` 的冻结/游标全部调用 reducer 的 `canFreezeFollow/lastSeqOf/nextDiscardFromSeq`，无第二套算法）。
- 正确层：store·文档状态机。
- 处置：纯投影算法唯一实现；`writePanel` 的 `signalCount/docShift` 只是**增量缓存**（与 `signalCountOf` 语义恒等、有测试锁定），不是第二套策略。

### P2-1（已核销）`LogHits.total` 与传输模型边界
- `total` 是窗口命中总数，用于 core 批切分不变量诊断（`batch.rs` 测试），**非死字段**；UI 不依赖它，不新增第二份语义。
- `LogLine` 作为 IPC 纯数据契约跨层（stack-layering「允许的契约孪生」），不引入多余镜像层（避免为分层而分层）。

### P2-2（已闭合·验证）文档容量口径
- 结论：**文档=缓存，环=历史边界**。`store.test.ts`「容量口径：重绑后只显示环仍持有的行（已被环淘汰的行不再显示）」以运行观察锁定：环淘汰后重绑，文档跟随环丢失旧行，不出现越界陈旧行。

- **本目标范围（日志消费投影平面：双通道临时对账 → 单一文档状态机 + 连续 seq 契约）＝ CLEAN。**

### 实现后数据通路证据（代码位置 + 运行观察）
- **实时命中**：`@yohu/api.onLogHits` → `capture-subscriptions.onLogHits`（只转发）→ `workspace.applyHits` → `panel-projection.applyHits` → `appendToSession` → `stream/log-window-reducer.applyAppend`（判连续/返回 `gap`）→ `writePanel` → store `visible`；若 `gap` → `deps.pageRequest(id)` → `viewport-page.loadPage` → `log.window.bind`。
