# 架构与性能优化审查（性能 + 纯 Rust 可行性）

- 日期：2026-11-23
- 范围：整机架构（`core/*` + `app/yohu-adbtools` + `ui/*`）的性能热点与"是否值得纯 Rust 化"
- 方法：只读源码 + 关键热路径逐行核对；不改代码。行号以本次快照为准。

---

## 0. 结论摘要（TL;DR）

1. **分层骨架是干净的，不要动。** core 零 Tauri、protocol 纯 wire、commands 薄转发、背压"丢信号不丢环"、投屏帧不进 JS、release 开 LTO/CU=1/strip/panic=abort——都是教科书级，保留。
2. **真正的性能热点只有一个：日志数据面。** 其余模块（终端/文件/设置/更新）没有同量级瓶颈；投屏解码/呈现已在原生 Rust 层（Media Foundation / VideoToolbox / VA-API），本就不进 JS，这块已是最优形态。
3. **纯 Rust（去 Tauri/WebView）技术上可行，但不建议大爆炸重写。** 要重写的是约 **7.7 万行 TS/TSX**（YoUI 4.0w + modules 2.6w + workbench 0.6w + api 0.5w）+ 整套设计系统，Rust 核心（约 2.8 万行）原样保留。最大收益点恰好只在日志列表一处——而这用 §2 的 4 个增量优化就能拿到 80%。
4. **性价比最高的四件事**（半天到 5 天）：`lines_from` O(1) 下标化 → `StoredLine` 用 `Arc<str>` + 锁外物化 → `replace` 条件化 → `log.range` 改列式二进制 IPC。

## 2. 性能热点与架构级优化（按 ROI 排序）

### P0-1　`log.range` 快照是 O(全环) 线性扫描，且持锁克隆
- 文件：`core/yohu-logsrv/src/ring.rs:79-86`（`lines_from`）
  ```rust
  self.buf.iter().filter(|line| from_seq <= line.seq).take(limit).map(Self::to_wire).collect()
  ```
  从**队首**线性过滤。UI 游标追到 10 万行环尾部时，每次拉取要扫 ≈10 万条谓词才命中第一行。
- 同文件 `for_each_from`（`167-205`）**已经**用 `seq - front.seq` 下标做 O(chunk)——`lines_from` 没跟上这套写法。
- `snapshot`（`220-223`）在**持锁**期间调 `lines_from` 并 `to_wire`（`66-77` 逐字段 clone：`ts/uid/tag.to_string/msg`），而采集侧 `push`（`139-156`）每行都要同一把 `Mutex<State>` → 高日志速率时锁争用（convoy）。
- 改：
  1. `lines_from` 用下标：`let start = from_seq.saturating_sub(front.seq) as usize; buf.range(start..(start+limit).min(len))` → O(limit)。
  2. 锁内只抓指针/下标，`to_wire` 的分配移到解锁之后（配合 P0-2）。
- 收益：拉取 O(10w) → O(5k)；锁持有从"全量克隆"降到"取指针"。

### P0-2　`StoredLine` 的 `msg/ts` 是 `String`，每次快照整段复制
- 文件：`core/yohu-logsrv/src/ring.rs:18-27`、`66-77`。因 `msg: String`，`to_wire` 必须 `msg.clone()` 且发生在锁内。
- 改：`msg: Arc<str>`、`ts: Arc<str>`（或把 ts 存成 epoch 毫秒 `u64`，展示时再格式化，省 23 字节/行）。`Arc` 让克隆退化为原子自增；配合 P0-1"锁外物化"，锁内近乎零分配。
- 备注：ts 每行唯一，`Arc<str>` 只为"避免再复制字节"；若要省内存，存 `i64` 毫秒最划算。

### P0-3　日志跨 IPC 走 JSON，是数据面最大固定成本
- 现状：`app/.../commands/log.rs:73-82` 返回 `Vec<LogLine>` → Tauri 默认 `serde_json` 序列化 → JS `JSON.parse` → 再构造对象。
- 量级：`DEV_PULL_BATCH = 5000`（`ui/.../capture-subscriptions.ts:55`），每 150ms 一批、每设备一趟，高负载可持续数 MB/s 的"序列化 + 解析"；且**每行重复字段名**（`seq/ts/pid/tid/level/tag/msg`），JSON 语法解析完全白费。
- 改（推荐）：`log.range` 返回 `tauri::ipc::Response::new(Vec<u8>)` 的**列式二进制**：
  ```
  [count u32]
  [seq: u64×count][pid: u32×count][tid: u32×count][level: u8×count]
  [tag_idx: u16×count]                 // 指向字符串表
  [msg_off: u32×(count+1)]             // 正文拼接区偏移
  [string_table: tag 字典 + 正文拼接]   // UTF-8
  ```
  JS 侧用 `ArrayBuffer` + `DataView` + 一次 `TextDecoder` 解码，零对象键名、零 JSON 语法解析。tag 已在内核驻留，字符串表体积也可控。
- 收益：数据面 CPU 预计降 50%+，GC 压力同步下降。这是"非纯 Rust"路线里能拿到的最大单项收益。

### P1-1　日志行进入 JS 后，消息正文最多存三份（Rust 环 + JS LogLine + 格式化副本）
- `docCap(bufferCapacity)`（`ui/.../viewport.ts:2-4`）**等于** bufferCapacity，默认 10 万 → `visible` 文档保留满 10 万行；`DocMessage.text`（`ui/.../editor/document.ts:22-31`）是格式化后的**又一份 msg 拷贝**（`line: row.line` 与 `source` 共享 `LogLine`，故 LogLine 不重复，但 `text` 是独立副本）。
- 即：稳态下消息正文 = Rust 环（1 份）+ JS `LogLine.msg`（1 份）+ JS `DocMessage.text`（1 份）= 最多 3 份；多会话 ×N。这解释了 perf 脚本"内存 < 800MB"的验收线（`scripts/verify-v6-logs-perf.ps1`）。
- 架构级选项（择一，需新 ADR，与 ADR-v6-006「过滤在 UI 消费者」有冲突）：
  - **(a) Rust 侧过滤 + 只传可见分页**：UI 只保留"视口页 ± 缓冲"，全文留在 Rust 环；滚动按需 `log.range`；过滤变更 → 一次 Rust 全环过滤（10 万行毫秒级）→ 返回命中。代价：过滤变更多一次 IPC（可接受）。收益：JS 内存从 O(bufferCapacity) 降到 O(视口)。
  - **(b) 原生列表表面**：见 §3 strangler，列表由 Rust 直接渲染，数据不出 Rust。

### P1-2　每物理行 `raw.replace('\r', "")` 无条件分配
- 文件：`core/yohu-logsrv/src/assembler.rs:31`。绝大多数行不含 `\r`，却每行新建 `String`。
- 改：`if raw.contains('\r') { Cow::Owned(raw.replace('\r', "")) } else { Cow::Borrowed(raw) }`（或用 `strip_suffix`）。高行速率下是纯白嫖的分配。

### P1-3　每设备每 150ms 一次 `spawn_blocking` 往返
- 文件：`app/.../commands/log.rs:79`。量不大，但可改为"常驻 blocking 读线程 + 通道"，或让 `snapshot` 在 `RwLock` 读锁下就地完成（写少读多，`RwLock` 比 `Mutex` 更合适；采集写、拉取读天然可分）。

### P2　低优先
- `RingStore.rings: Mutex<HashMap>`（`core/yohu-logsrv/src/ring_store.rs:20`）每次 `try_ring` 取全局锁；设备数少可不动，多设备可换 `RwLock`/分片。
- `VecDeque` 可换 `arraydeque`/`ringbuf` 降 alloc churn（收益小）。
- `capture-subscriptions.ts:83` 对每个会话 `appendRingLines` 逐批过滤；N 个同过滤窗口会 N 次过滤同一批。可按"唯一过滤键"去重算一次再分发（通常 1–2 窗口，收益有限）。

## 3. 纯 Rust 行不行

先厘清两种含义：
- **(A)** 核心保持 Rust，把桌面壳从 Tauri/WebView + SolidJS 换成纯 Rust 原生 GUI（egui/iced/Slint/…），目标是单语言、无 WebView 运行时依赖。
- **(B)** 只是"少用 JS / 重活进 Rust"——本项目**基本已做到**（解码/呈现/DnD/文件/采集全在 Rust）；再"纯"下去就是 (A)。

### (A) 的成本账
- 要重写的是 **UI 层，不是 Rust 核心**：YoUI ≈4.0w + modules ≈2.6w + workbench ≈0.6w + api ≈0.5w ≈ **7.7 万行 TS/TSX**，外加整套设计系统（token / 双主题 / 密度 / 动效）、右键菜单引擎（`defineContextMenu`/`openContextMenu`）、虚拟列表、ARIA/键盘可达、CJK 文本整形与 IME。
- Rust 核心（≈2.8 万行，含 logsrv/adb/files/mirror）**原样保留**——这是有利面。

### 框架务实对比
| 框架 | 形态 | CJK/IME | 虚拟化大表 | 可访问性 | 成熟度 | 结论 |
|---|---|---|---|---|---|---|
| egui | 立即模式 | 需装字体，IME 可用 | 手写 | 弱（accesskit 部分） | 高 | 原型快；正式产品对 CJK/无障碍偏弱 |
| iced | 保留(Elm) | cosmic-text 好 | 手写 | 改进中 | 中高 | 较稳妥 |
| Slint | 声明式 DSL | 好 | 手写 | 一般 | 中 | 性能/体积好；GPL/商业授权 + 自定义重 |
| Dioxus | 信号(类 Solid) | 好 | 手写 | 一般 | 桌面默认仍走 wry=WebView，Blitz 未成熟 | 心智模型最像，但"去 WebView"尚不成立 |
| Floem | 响应式 | cosmic-text 好 | 手写 | 弱 | 中低 | 编辑器类可用，生态小 |
| GPUI / Makepad | 自绘 | 参差 | 手写 | 弱 | 低 | 追求极致性能但工程风险高 |

### 性能真相
**WebView 的壳不是瓶颈。** 换成原生 GUI 真正能省的，恰好是 §2 的日志数据面——因为原生可以直接从 Rust 环渲染可见行，彻底消掉 JSON IPC 与 JS 第二份全文。所以"纯 Rust 的最大收益点 = 日志列表一处"，而不是整个应用。为一个模块重写整壳，投入产出比很差。

### 结论与推荐路径
**不建议大爆炸重写。** 若确要单语言 / 去 WebView，走 strangler：
1. 保留 Tauri + 现有 UI + 全部 core（不动骨架）。
2. 先把**日志列表区**换成**原生 Rust 子表面**——直接复用你已有的 `mirror` 把 D3D11/NSView 嵌进 Tauri 窗口的成熟做法（`app/.../mirror_present/*`），数据不出 Rust，WebView 只留外围 chrome。
3. 验证内存/帧率收益（对照 `verify-v6-logs-perf.ps1` 的 800MB 线）后，再决定是否把终端/文件也原生化。
4. 收益 ≈80%、成本 ≈10%、可回滚。

## 4. 建议执行顺序（按性价比）

| 序 | 动作 | 工作量 | 风险 | 收益 |
|---|---|---|---|---|
| 1 | P0-1 `lines_from` O(1) 下标化 | 半天 | 零 | 拉取 O(10w)→O(5k) |
| 2 | P0-2 `Arc<str>` + 锁外物化 | 1–2 天 | 低 | 锁争用大幅下降 |
| 3 | P1-2 `replace` 条件化 | 几十分钟 | 零 | 去掉每行无谓分配 |
| 4 | P0-3 列式二进制 IPC | 3–5 天 | 中（需前端解码 + 契约测试） | 数据面 CPU −50%+ |
| 5 | P1-1 窗口化 / 原生列表 | 1–3 周 | 中高（需新 ADR） | JS 内存 O(10w)→O(视口) |
| 6 | （战略可选）日志列表原生表面 strangler | 3–6 周 | 高 | 去 JSON、去第二份全文 |
| ✗ | 整体重写为 egui/iced | 6–12 月 | 高 | 收益主要已被 1–5 覆盖 |
