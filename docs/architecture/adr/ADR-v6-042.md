# ADR-v6-042 — Linux 投屏：有 VLD 用 libva，否则私有 CPU 仍出画

- **状态：** 已接受（2026-10-09）。实现在 `mirror_present/linux/`。`GtkWindow` 是单子控件，呈现表面是它的 GDK 子窗口，盖住 WebKit 洞，指针穿透。`probe().hevc` 仍报 `false`：HEVC Main 入口会查询并记日志，但还不能提交 HEVC 画面，避免 USB 默认 `h265` 选到一条没有的解码器。
- **日期：** 2026-10-09（同日修订：不再把「没有 `/dev/dri`」写成永久失败）
- **调研：** [调研-Linux投屏呈现与私有软解.md](../调研-Linux投屏呈现与私有软解.md)
- **补充：** [ADR-v6-028](ADR-v6-028.md)、[ADR-v6-030](ADR-v6-030.md)、[ADR-v6-032](ADR-v6-032.md)、[ADR-v6-026](ADR-v6-026.md)、[ADR-v6-043](ADR-v6-043.md)、[重设计-文件清单相位与Linux呈现.md](../重设计-文件清单相位与Linux呈现.md) 第 5 节

## 背景

043 交付了 Linux 工作台，并记下主窗 `GtkWindow` 指针。像素仍是占位：`probe().id = vaapi`，`hevc = false`，`spawn_surface` 走 `spawn_unimplemented`。`BindPipe` 把 `PresentBind` 写成 `Failed`。核对机没有 `/dev/dri`，Live 之后洞里是「没有画面」和「当前平台没有投屏硬解」。

上一版草案把「没有设备 / 没有 VLD」写成产品终点。Jessica 拒绝了。没有 DRM 的机器仍要出画。Windows 的 MF、DXGI、DComp 搬不过来；Linux 用自己的解码和呈现，不必镜像那条栈。

壳是 GTK 3（`gtk = "0.18"`）和 WebKitGTK 4.1。GTK 4 的 Wayland dmabuf 下沉对不上这个窗口。

## 决策

接受之后才实现。未接受时 043 第 5 条仍然有效。

1. **Linux 的 Convert 与 Present 只活在 `mirror_present/linux/`。** `FramePipe`、`Cmd`、`Stage`、`present_dest` 不动。`Picture` 仍是该后端的关联类型。硬解画面和 CPU 画面都不是跨平台 packed NV12，不进 `yohu-mirror`。不把 `windows/gpu.rs` 的 VP / HLSL / DComp 搬到 Linux。
2. **能打开 H.264 VLD 就用 libva。** `vaInitialize` 之后找 `VAEntrypointVLD` 上的 H.264 profile（High / Main / Constrained Baseline 任一即可）。不经过 FFmpeg、libavcodec、`ffmpeg-next`，也不使用 FFmpeg 的 vaapi 封装。scrcpy 的 `--hwdec=vaapi` 不移植。
3. **VLD 打不开就用 Linux 后端私有的 CPU 解码，并且仍然 Present。** 触发条件是下面任一，而不是产品终点：
   - 没有 `/dev/dri`
   - `vaInitialize` 失败
   - 打开的设备没有 H.264 VLD 入口
   CPU 解码器是运行时 `dlopen` 的 Cisco OpenH264，只在 `linux/` 内。`Caps.id` 保持 `vaapi`，不用 OpenH264 充当原生后端（030）。子控件照样创建。`PresentBind` 走 Loading，画出第一帧后走 Video。`mirror/painted` 从这次 Present 发出。
4. **两种画面进同一块 GTK 3 子控件。** 父级是 043 记下的 `GtkWindow`。子控件盖住 WebKit 透明洞，铺满 avail。可见卡片等于 `present_dest` 的 contain dest。
   - 有 VA 表面、当前会话是 X11：`vaPutSurface` 画进这块子窗口的 drawable。
   - 有 VA 表面、当前会话是 Wayland：用 `vaExportSurfaceHandle`（`DRM_PRIME_2`，只读、合成层）把 DMA-BUF 交给这块子控件。GTK 4 整窗下沉不在本 ADR。
   - CPU 画面：解码结果留在 `linux/`，用本目录的面积核变成要画的 RGB，在 GTK 主线程画进同一子控件。解码线程不碰 GTK。这和 030 把 AppKit 限制在主线程是同一条纪律，不是把 macOS 的 `NSView` 搬过来。
5. **五层归属。**

   | 层 | 硬解 | CPU 回退 |
   |----|------|----------|
   | Fit | 现成 `present_dest`。不选核 | 同左 |
   | Convert | libva H.264 VLD，1:1 到 VA 表面。不缩放 | OpenH264 解出本后端私有的画面。不缩放 |
   | Scale | 只在 `linux/`。缩小用面积核，或 GPU 对已导入表面的缩放 | 只在 `linux/` 的面积核 |
   | Compose | 子控件里的卡片 = dest | 同左 |
   | Present | 子控件翻页。`mirror/painted` 只从这一下发出 | 同左 |

   不引入 libplacebo、libswscale、libyuv、GStreamer。

6. **`probe` 的身份不变。** `id` 保持 `vaapi`，包括正在走 CPU 回退的时候。`hevc` 只在 VA 设备打开之后按 HEVC Main + VLD 查询。设备打不开时 `hevc` 仍是 `false`，会话按现有计划用 H.264。CPU 路径只解 H.264。HEVC 硬解不存在时不改用别的解码库。本版即使查到 HEVC Main，也先报 `hevc = false`，直到能提交 HEVC 画面。
7. **OpenH264 的许可闸门。** 依据 Cisco `BINARY_LICENSE.txt` v1.0：
   - `.deb` 不包含 Cisco 的二进制，也不包含我们自己编译的 `libopenh264`。二进制必须单独落到用户机器上。
   - 设置里可以关掉、再打开这份二进制。关掉之后，没有 VLD 的机器停在洞内说明，不静默换一个打进包里的解码器。
   - 控制这项的界面显示 `OpenH264 Video Codec provided by Cisco Systems, Inc.`
   - 关于页重现该许可全文，包括「使用方必须重现这些条件」那一条。
   - `.so` 还不在时，洞的标题仍是「没有画面」。正文说明缺的是这份可关闭的 OpenH264 二进制，不是「当前平台没有投屏硬解」，也不是「没有 `/dev/dri`」。二进制到位后同一次产品路径出画。文件怎么落到机器上见 [ADR-v6-044](ADR-v6-044.md)：用户点一下才从 Cisco 下载，启动时不静默拉取。
8. **有子控件之后回到 026。** 空态、失败、暂停由子控件上的同一份 `stage_copy` 绘制，删掉洞里的 Web 铬。子控件还没建起来时，继续用已经落地的洞内文案。
9. **截图。** Present 已经画出至少一帧之后，从最后一帧导出。在那之前不写空文件。

没有 VLD、并且 OpenH264 二进制也不可用或被用户关掉时，才是 `PresentBind = Failed`。仅仅没有 `/dev/dri` 不是这个状态。

## 明确不选

| 方案 | 为何不在这一 ADR |
|------|------------------|
| 没有 dri 就永久失败 | Jessica 已拒绝。scrcpy 的 `--hwdec=vaapi` 就是这档；他们的默认档是 `--hwdec=auto` |
| FFmpeg / libavcodec / ffmpeg vaapi | 028、030、032、043 仍禁止。要改见文末单独接受项 |
| 把 OpenH264 打进 `.deb` 或把它写成 `Caps.id` | 030 禁止冒充原生后端。Cisco 第 1 条还要求二进制单独下载 |
| 自编译一份 H.264 解码器放进包里 | BSD 版权不够。专利授权只跟着 Cisco 发布的那份二进制 |
| 把壳换成 GTK 4 才能出画 | GTK 4 dmabuf 下沉是好的 Wayland 设计，对不上 GTK 3 的 Tauri 壳。本 ADR 用 GTK 3 子控件 |
| Vulkan Video、GStreamer、libplacebo、WebCodecs、libswscale、libyuv | 028 / 032 / 024 已否决。GStreamer 的 `vah264dec` 也不当直播身份 |
| 克隆 Windows 的 Present | DXGI / DComp 不是 Linux 的表面。Fit 与 `Stage` 继续共用 |

## 单独接受项（本草案不接受）

若要用 FFmpeg 的软件 H.264 解码代替 OpenH264，必须另改这些已接受的句子，不能靠本页隐含：

- 028 §1「永远不走 FFmpeg」和否决里的「FFmpeg（CLI 与库）」
- 030 §1「不为 Linux 填 FFmpeg」
- 032 否决里的 FFmpeg / `libswscale`
- 043 §5「禁止 FFmpeg / libavcodec」

即便那份修订被接受，也只允许 `libavcodec` 出现在 `mirror_present/linux/` 的 CPU 回退里，`Caps.id` 仍是 `vaapi`，不进 Windows / macOS，不进 `yohu-mirror`。本草案不接受这项。

## 接受之后的顺序

1. `vaInitialize` 探针。有设备才查询 `hevc`。没有设备不把绑定写成永久失败，改走第 2 步的 CPU 分支。
2. 两条 Convert 都接到同一 GTK 3 子控件。VLD 成功走 libva。否则 `dlopen` OpenH264。`mirror/painted` 从画出的那一帧发出，`hasFrame` 和 fps 才开始为真。
3. 许可界面：开关、Cisco 那一行字、关于页全文。缺二进制时的洞内正文。
4. 删掉洞里的 Web 铬。空态 / 失败 / 暂停回到子控件上的 `stage_copy`。
5. Wayland 上的 DMA-BUF 导入可以接在同一子控件后面。不作为第 2 步的前提。核对用的 X11 VM 没有 `/dev/dri`，验收走 CPU 路径。

## 后果

- 已接受。043 第 5 条里「投屏像素仍不交付」改为「Linux 在 VLD 或可用的 OpenH264 二进制上出像素」。拖出仍不交付。FFmpeg 仍禁止。
- 没有 `/dev/dri` 的机器，包括这次的核对 VM，设计上出的是 CPU 画面，不是失败句。二进制还没单独下载时，洞里说明的是许可闸门。
- `Caps.id` 在 CPU 回退期间仍报告 `vaapi`。这是硬解身份，不是「已经在用 VA 表面」的运行标志。运行标志是 `PresentBind` 和 `hasFrame`。
