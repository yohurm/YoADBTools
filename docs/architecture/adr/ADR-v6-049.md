# ADR-v6-049 — 日志实时取数：水位信号 + 环形缓冲游标拉取（对齐 LogCat）

- 状态：已采纳
- 日期：2026-11-20
- 关联：ADR-v6-006/007/021/041/046/047/048、[日志实时取数分析](../../reviews/日志实时取数-现状与LogCat对齐.md)

## 背景

实时更新靠 `log/hits` 携带正文批次推给 UI；`try_send` 满即丢（丢推送不丢环），UI 只在整页 `log.window.bind` 时读环。切应用/后台使事件队列满 → UI 文档缺一段，环淘汰后不可补。Android Studio Logcat 是「IDE 内消息环/文档为数据源，视图去读」，与我们的「推送正文」模型不同。

## 决策

1. 环形缓冲是唯一实时数据源；UI 每窗口持**全局 seq 游标**。
2. `log/hits` 改为**每设备水位信号** `LogAppended{serial,last_seq}`（不含正文，无 window_id）；`last_seq` 是设备环最新 seq。
3. UI 收到信号后对**该设备每个在采窗口**调用 `log.range(serial, from_seq, limit)` 从环**按 seq 拉原始行**，过滤仍在 UI（ADR-v6-006）；拉齐到 `last_seq`。
4. 丢弃信号只影响延迟：下一次水位更高即可一次补齐；容量内不丢。
5. 删除 `LogHits.tail`、`Batcher` 正文聚合、`WindowBook` 命中索引、`LogPage/LogWindowBind` 与 `log.window.bind/release`、`LogOverflow`；初始页/换过滤也走 `log.range`，不再有整页 bind。

## 后果

- 切应用/后台丢推送不再丢日志（受环容量约束，ADR-v6-021）。
- `log/hits` 体量从「正文数组」降为「水位」；事件通道压力显著下降。
- **每设备只发一趟拉取**：`onLogAppended(serial)` 由设备级拉取泵单飞执行 `log.range`，把同一批原始行分发给该设备所有在采窗口（各窗口自行过滤/投影）。窗口数 N 不再放大 IPC 与环克隆成本。
- **`log.range` 为异步 + 阻塞线程池**（`spawn_blocking`）：环快照克隆/序列化不在 Tauri 主线程，避免高频拉取压死 UI 事件循环。
- **UI 拉取硬守卫**（防热循环）：未开始采集（`fromSeq<0`）不拉；单次最多 50 轮；每批后若窗口 `lastSeenSeq` 未前进立即停止；环为空的重绑只按新过滤重筛已画行、不清空。
- **过滤语义变化统一走重绑**：换过滤 / 包名 PidSet 变化 / 首次开始都是「重置游标 + 从环重建」；恢复/暂停/回前台只是增量 `catchUp`。

## 教训（本次“开发窗口卡死”）

旧实现 `onLogAppended` 对**每个窗口**各自拉环，且拉取循环在消费端拒绝（未开始/暂停/并发重置）时不校验游标是否前进 → 同一批被反复重拉，窗口/信号一多形成拉取风暴：WebView 渲染进程与主进程长期 100% CPU、工作集涨到 GB 级、窗口无响应。上面的设备级单飞、异步命令与游标前进守卫是针对该架构缺陷的根因修复。

## 不引入

不引入兼容层；不做「推送正文 + 拉环」双轨。过滤仍在 UI，不搬进 core。
